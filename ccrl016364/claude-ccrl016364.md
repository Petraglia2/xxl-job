# xxl-job admin 端 CronExpression.java 讲解

> 面向刚接手本项目的后端工程师。从「它是什么 / 在项目里干什么」讲起，再逐层深入到内部机制和维护时要小心的坑。
>
> 文件位置：`xxl-job-admin/src/main/java/com/xxl/job/admin/scheduler/cron/CronExpression.java`

---

## 一、一句话定位

`CronExpression.java` 是一个 **Cron 表达式的「解析器 + 计算器」**：把一个像 `0 0 2 * * ?` 这样的字符串，翻译成「下一次该在什么时刻触发」。它是 xxl-job 调度的**时间大脑**——决定每个 CRON 类型的任务什么时候跑。

文件头第 18 行写得很清楚：`Borrowed from quartz v2.5.2`。**它不是 xxl-job 自己写的**，而是从著名调度框架 Quartz 整段搬过来、放进了 `com.xxl.job.admin.scheduler.cron` 包。这一点很重要，后面讲维护时会再提。

---

## 二、它在本项目里被谁调用（这是你最该先记住的）

生产代码里只有**两个真正的入口**：

| 调用方 | 调用的方法 | 作用 |
|---|---|---|
| `XxlJobServiceImpl.java:89` / `:195` | `CronExpression.isValidExpression(conf)` | **新增/编辑任务时校验** 用户填的 Cron 合不合法，不合法就返回报错 |
| `CronScheduleType.java:14` | `new CronExpression(conf).getNextValidTimeAfter(fromTime)` | **调度核心**：算出这个 CRON 任务下一次触发时间 |

```java
// CronScheduleType.java:14 —— 整个 CRON 调度就指着这一行
return new CronExpression(jobInfo.getScheduleConf()).getNextValidTimeAfter(fromTime);
```

所以你只要先吃透两个公开方法 —— `isValidExpression(校验)` 和 `getNextValidTimeAfter(算下次)` —— 就掌握了它对外的全部价值。其余的（`util/old/XxlJobDynamicScheduler` 是重构前的旧 Quartz 调度；`CronExpressionTest` 是单测）可以先放一边。

## 三、先纠一个最容易踩的认知坑：这是「7 段」格式，不是 Linux 的「5 段」

很多人拿 Linux crontab 的习惯来用，会直接出错。这个类用的是 **Quartz 格式**，字段顺序是（见类注释第 41–102 行）：

```
秒    分    时    日    月    周        [年(可选)]
0-59  0-59  0-23  1-31  1-12  1-7       空 或 1970-2199
```

两个关键差异：

1. **第一段是「秒」**，不是分钟。`0 0 12 * * ?` = 每天中午 12:00:00。Linux 的 `* * * * *` 在这里会解析错位。
2. **星期从 1=周日 开始**（`dayMap`，第 243–249 行：`SUN=1 ... SAT=7`），不是 Linux 的 0=周日。

还有一条 Quartz 的硬性限制（第 519–527 行）：**「日」和「周」不能同时指定**，必须有一个填 `?`。所以你会经常看到 `0 0 2 * * ?`（按日）或 `0 0 2 ? * MON-FRI`（按周）这种写法 —— 那个 `?` 不是可有可无，是规则要求。

特殊字符速查：

| 字符 | 含义 | 例子 |
|---|---|---|
| `*` | 所有值 | 分钟写 `*` = 每分钟 |
| `?` | 不指定（只用于 日/周） | 见上 |
| `-` | 区间 | 时写 `8-18` |
| `,` | 枚举 | 周写 `MON,WED,FRI` |
| `/` | 步长 | 秒写 `0/15` = 0,15,30,45 |
| `L` | last，最后 | 日写 `L`=月末；周写 `6L`=最后一个周五；`L-3`=倒数第3天 |
| `W` | 最近的工作日 | 日写 `15W`=离15号最近的工作日 |
| `#` | 第几个星期几 | 周写 `6#3`=本月第3个周五 |

## 四、核心心智模型：它分「两个阶段」工作

理解这个类，只要抓住两段式：

```
                  ┌─────────── 阶段1：解析(构造时一次性完成)──────────┐
new CronExpression("0 0/15 8-18 * * ?")
                  └─> 把字符串拆成 7 个字段，每个字段算出「哪些值是开着的」
                      存进一组 TreeSet<Integer>(有序集合)

                  ┌─────────── 阶段2：计算(每次问"下次几点"时)──────┐
getNextValidTimeAfter(now)
                  └─> 从 now 往后，一个字段一个字段地"对齐"到下一个允许的值
                      直到所有字段同时满足 → 那个时刻就是答案
```

### 阶段 1：解析 —— 把表达式变成一堆「有序集合」

调用链：**构造函数 → `buildExpression` → `storeExpressionVals` → `checkNext` → `addToSet`**。

- **构造函数（279 行）**：先把表达式 `toUpperCase`（所以大小写不敏感），再交给 `buildExpression`。
- **`buildExpression`（447 行）**：按空格把表达式切成最多 7 段；`exprOn` 这个变量记录当前在处理第几段（`SECOND=0 ... YEAR=6`）。每段再按逗号拆开，逐个交给 `storeExpressionVals`。
- **`storeExpressionVals` / `checkNext`（536、740 行）**：这是真正解析单个片段的地方，处理 `*`、`/`、`-`、`L`、`W`、`#`、`JAN`、`MON` 等所有语法。
- **`addToSet`（981 行）**：做合法性校验（比如秒必须 0–59，第 987 行），然后把这个字段「开着的值」全部塞进对应的 `TreeSet`。

最终，每个字段都变成一个**有序整数集合**（第 254–261 行）：

```java
protected transient TreeSet<Integer> seconds, minutes, hours,
        daysOfMonth, months, daysOfWeek, years;
```

举例 `0/15` 在秒字段 → `{0, 15, 30, 45}`；`8-18` 在时字段 → `{8,9,10,...,18}`。

> **为什么偏偏用 `TreeSet`（而不是 List/HashSet）？** 因为 `TreeSet` 是排序的，它的 `tailSet(x)` 能瞬间给出「所有 ≥ x 的值」。而阶段 2 要反复问的正是：「比当前这一秒大、且被允许的下一个值是谁？」—— 这是整个设计的点睛之笔，直接决定了阶段 2 的算法形态。

两个**哨兵常量**要认识（第 219–220 行）：`*` 在内部记成 `ALL_SPEC=99`，`?` 记成 `NO_SPEC=98`。它们是「标记位」，不是真正的时间值。

### 阶段 2：计算 —— `getTimeAfter` 是整个文件的心脏（1185 行）

这是最值得读懂的方法。它的算法本质是一个**「对齐 + 重来」的循环**（不断逼近，直到收敛）：

> 从「给定时刻 + 1 秒」开始，按 **秒 → 分 → 时 → 日 → 月 → 年** 的顺序，每个字段用 `tailSet` 找「≥ 当前值的、最小的合法值」。
> - 如果找得到 → 这个字段对齐成功，继续看下一个更大的字段。
> - 如果找不到（本字段没有更大的合法值了）→ 把本字段回绕到最小值、**给上一级字段 +1**，然后 `continue` **整个循环从头再来一遍**。

为什么找不到就要「从头重来」？因为一旦你把「时」进位了（比如从 23 点跳到次日 0 点），那么「日」可能变了、「月」甚至「年」都可能变 —— 下面所有字段都得重新对齐。所以它不修修补补，而是回到循环顶端整体重算。代码里那一连串 `cl.set(...); continue;` 就是在干这件事。

**跑一遍具体例子**，表达式 `0 0 2 * * ?`（每天 2:00:00），当前 `2026-06-13 03:30:00`：

1. +1 秒 → `03:30:01`
2. **秒**：要 `{0}`，当前 1，没有 ≥1 的 → 回绕到 0，分钟进位到 31
3. **分**：要 `{0}`，当前 31，没有 ≥31 的 → 回绕到 0，小时进位到 4 → 分钟变了，**重来**
4. 重来到 `04:00:00`。秒 0✓ 分 0✓。**时**：要 `{2}`，当前 4，没有 ≥4 的 → 回绕到 2，日进位到 14 → 小时变了，**重来**
5. 重来到 `2026-06-14 02:00:00`。秒✓分✓时✓。**日**：`*` 允许所有，14 号 OK。月✓ 年✓ → `gotOne = true`
6. 返回 **`2026-06-14 02:00:00`** ✅

整个过程就是「哪一档不满足，就把它顶到下一个合法刻度，并把更低的档归零、更高的档进位，然后重算」，直到六个档同时咬合。

代码里还有两道**死循环保险**：`year > 2999` 直接返回 null（1202 行），`year > MAX_YEAR` 也返回 null（1478 行）。`MAX_YEAR` 是「当前年 + 100」（第 267 行），类加载时算一次。

## 五、几个「魔法」实现，读源码时别被绕进去

这些是 Quartz 的精巧（也烧脑）之处，提前打个预防针：

1. **`L` / `L-n`（月末偏移）用魔法数字编码**。日字段里看到 32–62 这种数，不是真的日期，而是「距月末的偏移」的编码：`LAST_DAY_OFFSET_END=62` 代表纯 `L`（月末），`L-3` 就是 `62-3=59`。它在 `findSmallestDay`（1648 行）里被解码回真实日期。**不懂这套编码就去改解析，几乎一定会埋 bug。**

2. **`W`（最近工作日）单独存**。它不放进 `daysOfMonth`，而是放进独立的 `nearestWeekdays` 集合（第 258 行），在 `getTimeAfter` 里做「周六往前挪、周日往后挪、不跨月」的修正（1295–1303 行）。

3. **`6L` 和 `6#3` 用单独的标志位**：`lastDayOfWeek`（布尔）和 `nthDayOfWeek`（整数）（第 263–264 行），不是塞进集合里的。

4. **「日」的计算分三大支**（1276 行起）：按日规则 / 按周规则（周里又分 `L`、`#`、普通三种）/ 两者都填（直接抛 `UnsupportedOperationException`）。这是 `getTimeAfter` 里最长最绕的一段，读的时候按这三支拆开看。

5. **`Calendar` 是 0 起的、Cron 是 1 起的**。所以你会看到满屏的 `+1`/`-1`（比如 `mon - 1`），都是在这两套月份编号之间转换。看到别慌，这是噪音不是逻辑。

6. **区间会「回绕」**（`addToSet` 1078–1094 行）：`FRI-MON`、`22-2` 这种右边比左边小的，会自动跨周/跨天展开。

## 六、公开 API 速查（你实际会用到的）

| 方法 | 用途 | 备注 |
|---|---|---|
| `new CronExpression(str)` | 构造，顺带解析 | 非法表达式抛 `ParseException` |
| `isValidExpression(str)` | 校验是否合法 | 静态，返回 boolean；**本项目保存任务时用它** |
| `getNextValidTimeAfter(date)` | **算下一次触发** | **调度核心**；内部就是 `getTimeAfter` |
| `isSatisfiedBy(date)` | 某一秒是否命中 | 忽略毫秒 |
| `getTimeBefore(date)` | 上一次触发 | 用二分法反推，非精确直算 |
| `setTimeZone(tz)` | 设时区 | 不设则用 JVM 默认时区——**跨时区部署务必注意** |

## 七、维护时的注意事项（给接手人的提醒）

- **它是 Quartz 的「搬运副本」**。发现 bug 或要升级，正确姿势是**和上游 Quartz 2.5.x 对比**，而不是凭感觉硬改 —— 这套解析逻辑边界 case 极多，自己改很容易顾此失彼。本分支那一串 `代码解析对比` 的提交，看名字也是在做这件事。
- **校验入口要对齐**。前端/接口允许用户填 Cron，真正的合法性闸门是 `XxlJobServiceImpl` 里的 `isValidExpression`。改 Cron 相关校验时别漏了这里。
- **时区**：`getNextValidTimeAfter` 不带时区参数，用的是 `getTimeZone()` 的结果（默认 JVM 时区）。集群跨时区时，这是排查「触发时间差几小时」类问题的第一嫌疑点。
- **`transient` 与序列化**：那些集合都是 `transient`，反序列化时靠 `readObject`（1673 行）用原始字符串重新解析重建 —— 所以这个对象能安全地被序列化传输。
- **性能**：`getNextInvalidTimeAfter` 源码里自己标注了「性能很差」（366 行），正常调度用不到它，别在热路径上调。

---

**一句话收尾**：这个类做的事就两件 —— 进门时把 Cron 字符串**解析成一组有序集合**，之后每次用「对齐到下一个合法刻度、不行就进位重来」的循环**算出下一个触发时刻**。xxl-job 的 CRON 调度，本质上就是不停地拿上次触发时间去问它「下一次几点」。建议你打开 `CronExpressionTest`（它跑 `0 0 0 ? * 1` 打印未来 5 次触发），改几个表达式跑一跑，十分钟就能把手感建立起来。
